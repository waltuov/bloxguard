# Known limits

bloxguard reports what it can see without running code. These gaps are known. The [README](../README.md#what-it-cant-see) has a short version for game developers, and the summary below links to the details of each group.

A few terms used below: a value is *folded* when the scanner works out its exact value without running code, such as `tonumber("999" .. "000")`. A *candidate* is one of several possible values of a target, listed when the scanner cannot tell which one is used. An input is *partial* when bloxguard could not read or check all of it. A partial or failed input makes the scan incomplete, and an incomplete scan exits with code 2 unless you pass `--allow-incomplete`.

## Summary

- **A scan is one review step.** It sees only the files you give it, not code or data fetched at runtime, such as `HttpService` responses or assets that BG007 reports as loaded. A finding does not prove intent, and a clean result does not prove that an asset is safe. It does not replace Roblox sandboxing, account controls, or manual review. [Details](#scope-of-a-scan)
- **Medium findings pass by default.** With the default `high` threshold, also the Action's default, a scan whose findings are all medium or low exits 0. Purchase prompts and teleports in inserted content, package links, unusual script placement, deceptive names, and obfuscation on its own are medium. Use `--fail-on medium` (`fail-on: medium` in the Action) for third party models. [Details](#medium-findings-pass-the-default-threshold)
- **Incomplete scans.** A script that does not parse, data a rule needs that cannot be read, an unknown class that may hide code, or a reached limit makes the scan incomplete. The output marks the input `partial` with the reasons, and the exit code is 2 unless you pass `--allow-incomplete`. A luau-lsp type declaration file such as `testez.d.lua` gets a note instead, because Roblox does not run it. So does a property value type that is newer than the file decoders, such as the one current Studio writes on `Terrain`, when no rule reads the property and its class cannot hold code. [Details](#incomplete-scans)
- **Rojo projects are approximated.** A folder scan reads every `.lua` and `.luau` file but does not apply the project file's mapping, so instance paths follow your folders. Data files such as `.txt`, `.toml` or `.csv` are not read. A project file that pulls in content the scan cannot see, or sets properties that rules read, makes the scan incomplete. For full fidelity, run `rojo build` and scan the output. [Details](#rojo-projects-and-source-trees)
- **Some backdoors leave no telltale code.** A clone virus that copies its script into every part, without `require`, `loadstring` or an HTTP call, acts only at runtime, and no rule reports the copying. Text that asks you to enable HTTP requests gets no finding, and neither does `game:HttpGet` on its own. The usual `loadstring(game:HttpGet(...))` is BG003, and a webhook call is BG008. [Details](#backdoors-with-no-telltale-code)
- **IDs that only exist when the code runs.** The scanner does not run loops, decoders, VM style loaders or buffer code. A `require` of an ID built that way gets a lower confidence or a low finding instead of a resolved ID. BG005 may still report the obfuscation. [Details](#values-that-need-running-code)
- **Values the scanner cannot follow.** Each script is analyzed on its own. An ID passed between scripts through `_G` or `shared`, returned by a ModuleScript, or loaded through a wrapper in another ModuleScript gets a low confidence finding. Objects found through `GetChildren()` or a computed name, IDs in properties the scan does not load such as a Sound's `SoundId`, values in tables that reach code the scanner cannot see, deep `__index` chains and wrapper calls past the replay limits also give lower confidence. A property write through a method name built at runtime is missed, and objects renamed or moved at runtime are still found by their names in the file. Scan the project folder or the built place, not a loose file, so paths such as `script.Parent.Parent.State.Value` can be resolved. [Details](#values-the-scanner-cannot-follow)
- **Trusted IDs.** A trusted ID removes a finding only when the `require` argument is a constant. A trusted ID read from a configuration table, value object, attribute, global or function parameter is still reported at medium confidence, so suppress such a reviewed loader by path. [Details](#trusted-ids)
- **Resource limits.** Size, count, attribute, nesting, analysis step, path, output and per input time limits bound the work, and reaching one makes the scan incomplete. The time limit is checked between steps, so one parser call can finish after it. [Details](#resource-limits)
- **File formats.** XML files may nest at most 2,048 `Item` elements, and a deeper file is incomplete. Binary files do not mark which strings are script source, so on a class the bundled reflection database does not know, a string counts as code only when it parses as Luau. [Details](#file-formats)
- **Known false positives.** Analytics that sends `player.UserId` and server browsers that post `game.JobId` (BG008), command bar tutorials (BG012), building tools that keep scripts inside parts (BG006), admin systems loaded by a reviewed ID and registries that store `require` (BG001), your own packages (BG011), and emulators, test runners and Studio plugins that run code on purpose (BG003, BG004). Review each finding and suppress it with a reason when it is expected. [Details](#known-false-positives)

## Scope of a scan

bloxguard sees only the files and source text you give it. It cannot see code fetched later from the internet. A finding does not prove intent. A clean result does not prove that an asset is safe. The scanner is one review step and does not replace Roblox sandboxing, account controls, or manual review.

- **Data fetched at runtime.** Responses from `HttpService`, DataStores, `MarketplaceService`, and other services are not visible offline. BG007 reports runtime asset loads, but the loaded content is not scanned.

## Medium findings pass the default threshold

- **The default threshold passes medium findings.** With the default `high` threshold, also the Action's default, a scan whose findings are all medium or low exits 0. Several common free model shapes are medium by design: purchase prompts and teleports started by inserted content (BG010), external package links (BG011), obfuscation (BG005, high only next to a high BG001 to BG004 finding in the same script), and unusual placement or deceptive names (BG006). When you review third party models, use `--fail-on medium` (`fail-on: medium` in the Action).

## Incomplete scans

An unknown class is listed as an informational diagnostic when its contents remain readable. It makes the scan incomplete if it may hide source, a property that can hold code, or a property used by a rule. Unreadable rule inputs (such as attribute data that does not decode), parse failures, and exceeded limits also make a scan incomplete. A type declaration file for luau-lsp, such as `testez.d.lua` with `declare function it(...)`, is the exception: Luau does not compile that syntax as a script, so Roblox runs none of it, and it gets an informational note instead (see [configuration](configuration.md#type-declaration-files)). A property value type that is newer than the file decoders, such as the one current Studio writes on `Terrain`, is skipped. It gets a note when no rule reads the property and its class cannot hold code, and makes the scan incomplete otherwise (see [configuration](configuration.md#unknown-classes)). An incomplete scan returns a nonzero exit unless you explicitly pass `--allow-incomplete`.

## Rojo projects and source trees

Direct source tree scans approximate Rojo naming and metadata. They scan every `.lua` and `.luau` file in the tree but do not apply project mappings. A Rojo `*.project.json` file is checked and listed as a note. It makes the scan partial only when it pulls in content the direct scan cannot see: a `$path` outside the scanned folder or inside an excluded folder, inline properties or attributes that rules read, or a project file that cannot be read or parsed. For full Rojo fidelity, run `rojo build` in your own CI and scan the output.

- **Rojo mappings.** Direct source tree scans do not apply project mappings, so instance paths follow the folder layout and property lookups can differ from the built place. Data files that Rojo turns into instances, such as `.txt`, plain `.json` or `.jsonc`, `.toml`, `.yaml`, and `.csv` files, are not read, and metadata that sets `Source`, `Value` or attributes on one makes the scan partial. Model and metadata files are read with the `.json` or `.jsonc` extension, as Rojo 7.7 reads them. Build with Rojo and scan the output for full fidelity.

See [source trees and Rojo](configuration.md#source-trees-and-rojo) for every rule.

## Backdoors with no telltale code

- **Self-replicating scripts.** A clone virus that copies its own script into every part, without `require`, `loadstring` or an HTTP call, acts only at runtime. No rule reports the copying.
- **Lure text.** Text that asks a developer to enable HTTP requests, for example "for better performance", is not BG012, which needs a command surface such as the command bar. The webhook call that the setting enables is BG008. `game:HttpGet` is not one of the HTTP calls BG008 reads, so on its own it gets no finding. The usual `loadstring(game:HttpGet(...))` is BG003.

## Values that need running code

- **Values that need execution.** The scanner does not run loops. A variable or table field changed inside a loop is unknown inside and after the loop. Its value from before the loop and the literals and loop values assigned to it stay candidates, so a `require` of it gets BG001 high with medium confidence that lists the ID shaped candidates, and a trusted ID among them does not remove the finding. A value from a decoder that the bounded evaluator cannot replay, or from a VM style dispatch loop, is not folded either. BG005 may still report the obfuscation shape.
- **Buffers and `string.pack`.** Values written into a `buffer` or packed with `string.pack` and read back are not folded, so an ID rebuilt that way gets a low BG001 finding. When the whole ID is still visible in the `require` expression, such as `require(roundtrip(999000000000001))`, the finding is high with medium confidence and names it as an `asset id literal`. Folding these values is planned for v0.2.

## Values the scanner cannot follow

- **Wrappers in another module.** A function in the same script that passes its argument to `require` is checked at each call site, including methods, `__call`, `__index`, `__newindex` and operator metatables, `gsub` callbacks, coroutines, and class style constructors. Replay stops at a depth of 3, 16 calls per function, and 128 per script; past that, an ID shaped argument, also inside a table argument up to three levels deep, still gets a medium confidence BG001 finding when the function holds or calls a `require` whose target may be something other than a local module. A function that only requires local modules, such as a lazy `require(script.Parent.Util)`, gets none. A wrapper in another ModuleScript is not followed, so only the `require` inside it gets a low confidence finding.
- **Values shared between scripts.** Each script is analyzed on its own. A value that one script stores in `_G` or `shared` and another script passes to `require`, and an ID that a ModuleScript returns, are not followed, so that `require` gets a low confidence BG001 finding. Within one script, values stored in `_G`, `shared` or through `getfenv()`, under a name or an integer key, are followed. Following values across scripts needs a pass over every script of a file before the analysis, which is planned for v0.2. Instance writes are the exception: a property or attribute that any script of the file writes is never reported as resolved (BG002), unless the write calls a method whose name is built at runtime (see Instance writes).
- **Tables and closures.** A table that may reach code the scanner cannot see, such as an unknown function, `table.sort`, a return from a function other code can call, or a local function above 16 KiB or past the replay limits, is treated as changed: its values stay candidates next to an unknown value. A function read where it is defined sees later writes of the same script to the variables it reads and to the tables those writes may reach, but not a change that code the scanner cannot see makes later to a table it reads. A field write through a path, a call result, a parameter or a global counts for that key of every table except one whose local is only ever indexed, so its value can be a candidate of an unrelated table. A write through a table's own local also counts for the tables the script stores under the key `__newindex` when the script passes that table to `setmetatable` with such a metatable. When the scanner cannot tell which tables get one, such as after a `setmetatable` on a parameter, a write through any such local that is used as a value counts for them, so its value can be a candidate of an unrelated table. A metatable that code the scanner cannot see copies onto a table is not followed. A `__newindex` stored under a computed or backtick key is not seen, so a function that reads the target table misses a later write through that proxy. A `newproxy` metatable is not followed. A closure that a factory returns, such as `make(id)()`, is checked with the values the factory received; called after the factory returned, it reads the factory's locals as unknown.
- **`__tostring` metamethods.** The `__tostring` function that `print`, `warn`, `tostring`, `string.format` and interpolated strings call on a value is not followed. A `require` inside it is reported on its own terms, but a call it makes to a function assigned elsewhere is not traced back to the value that triggers it. This also holds inside a closed output capture, so a capture that formats such a value keeps its BG004 low.
- **`__index` chains.** The first 8 tables of an `__index` chain are followed exactly, for string and integer keys alike. A value found further down the chain, up to `max_depth` tables, is a candidate next to an unknown value, so an ID there gets BG001 high with medium confidence; past `max_depth` tables the value is unknown.
- **Instance writes.** Property and attribute writes are found by a pass over the tokens of every script. A name the pass cannot read counts as every name. A method name built at runtime, such as `obj[("Set") .. "Attribute"](obj, "id", v)`, is not seen as a write, and objects renamed or moved at runtime are still found by their names in the file.
- **Objects the scanner cannot pin down.** An element of `GetChildren()`, a child found by class or by a computed name, and the target of an `ObjectValue` are not resolved to one object. A `.Value` or attribute read on them gets BG002 with low confidence. It is critical when the closest known object or anything below it stores an ID shaped value, and medium otherwise, like a `.Value` on a path that leaves the scanned content. A loose file has no folders around it, so scan the project folder or the built place to resolve paths such as `script.Parent.Parent.State.Value`.
- **ID properties the scan does not load.** Place and model files are read for script sources and run settings, value object values, attributes, shown text and package fields, not for every property. An ID stored in another property, such as an Animation's `AnimationId` or a Sound's `SoundId`, and read by a script, such as `require(tonumber(anim.AnimationId:sub(14)))`, is BG002 at medium severity with low confidence, not critical.

## Trusted IDs

- **Trust.** A trusted ID removes a finding only when the `require` argument is a constant: literals and locals declared once from such values. Another variable with the same name does not change this. A configuration table, a value object, an attribute, a global or a function parameter that holds a trusted ID is still reported at medium confidence, so suppress such a reviewed loader by path.

## Resource limits

Size, count, attribute, parser depth, analysis step, path, output, and per-input time limits bound local work. The time limit is one budget per input, shared by loading, analysis, and inventory, and it is checked cooperatively between steps. It is not hard process isolation, so one parser call can finish after the requested time. See [configuration](configuration.md) for defaults and controls.

- **Analysis budgets.** Each script has fixed caps on nesting and expression size and a step budget (see [configuration](configuration.md)). A concatenation chain may have up to 8,192 `..` operators. Evidence quotes at most 4 KiB of source.

## File formats

XML inputs have a fixed safe parser cap of 2,048 nested `Item` elements. Exceeding it makes the input partial.

- **Binary files and unknown classes.** Binary files do not mark which strings are script source. On a class the bundled reflection database does not know, a string counts as code only when it parses as Luau.

## Known false positives

- **Known false positives.** Analytics that sends `player.UserId`, and a server browser that posts `game.JobId` and `game.PlaceId` to its own backend (BG008). Tutorials that explain the command bar (BG012). Building tools that keep scripts inside parts (BG006). Admin systems loaded by a reviewed ID (BG001, see `trusted_asset_ids`). Tables or registries that store `require` as a value, which BG001 reports at high severity by design. Packages your team owns (BG011). Emulators, test runners and Studio plugins that build and run code on purpose, with `loadstring`, `setfenv` or `getfenv(fn)` (BG003, BG004 high); suppress them by path. A test spec that reads its runner's functions with `getfenv().it`, or captures output by saving `getfenv(fn).print` or `.warn`, putting in a local function and putting the saved value back, gets only low BG004 findings (see [BG004](rules/BG004.md)). Review each finding and suppress it with a reason when it is expected.
