# BG001: numeric module load

Default severity: high. Confidence is high when every possible value of the target is known and medium when the target only looks like an ID, may hold a value the scanner did not see, or holds a trusted ID that trust does not remove (see Suppression). An unknown target is low severity and low confidence.

## What it detects

BG001 reports `require` calls that use a numeric asset ID. It follows aliases and bounded constant expressions, including arithmetic, string to number conversion, constant table indexes, type casts, `or`, if-expressions, and common string and math library calls. It also reports values that the scanner cannot resolve as local code, at low severity and low confidence.

A target can have several possible values, for example after an `if`. When all of them are known, each asset ID among them gets its own finding with high confidence. The evidence says `resolved asset id` when there is one ID and `asset id candidate` when there are several. Among several possible values, `0`, numbers below 1,000,000, `nil`, and empty strings are ignored.

When some possible values are unknown, the finding is high with medium confidence and lists the known IDs as `asset id candidates`, never as resolved. A target that contains an integer of at least 1,000,000 or a run of 7 or more digits that cannot be folded at all is reported the same way, with the digits as `asset id literal`, and so is a target downloaded at runtime. A value may also have been changed out of the scanner's sight:

- A variable or table field changed in a loop is unknown inside and after the loop. Its value from before the loop stays a candidate, and so does each literal or loop value assigned to it.
- A function body is first read where it is defined, and it may run later. Inside it, a variable of an enclosing scope that the script assigns again, a global the script assigns, and a field of a table from outside read as their current value and every value the script assigns to that variable, or to that field of a table the write may reach, with an unknown value for anything that is not a literal. A field written under a computed key counts for every key of the tables that write may reach. Such a function, and one that writes such a variable or table, is checked again at every call, so `id = 999000000000002; load()` judges `load` with the new value.
- A table that may reach code the scanner cannot see is treated as changed: an unknown function or method that receives it, a store into `_G`, `shared`, a global or an instance, a return from a function that other code can call, a use as a table key, an `error` value, `table.sort`, a `table.move` the scanner cannot follow, an unknown metatable, a `__newindex` metatable, or a local function that cannot be replayed.
- A write through a variable or field that a loop or a later call may have changed. A table stored there afterwards is treated as changed, and the written value becomes a candidate of changed tables.
- An `__index` chain longer than 8 tables. The first 8 are followed exactly, for string and integer keys alike; a value found further down, up to `max_depth` tables, is a candidate next to an unknown value.
- A candidate set that reached its size cap.

Each name is the variable it refers to by Luau's scope rules, also when a function is checked again at a call. A parameter, a loop variable or a local of another block that has the same name is another variable, and a write to it changes nothing else. A field write counts only for the tables it may reach. A write through a local that is declared with a table constructor, or as an alias of such a local, and never assigned again reaches only the tables of that constructor. It also reaches the tables the script stores under the key `__newindex` when a metatable may send it there: when the script passes that table to `setmetatable`, directly or through an alias, with a metatable that may hold a `__newindex` table. When the scanner cannot tell which tables get such a metatable, a write through any such local that is used as a value reaches them too. That is the case for a `setmetatable` on a parameter, a field or a call result, a `__newindex` metatable used other than as the metatable of a `setmetatable` call, a `__newindex` stored into a table the scanner cannot place, `getmetatable`, and `setmetatable` used other than as a direct call of the global. A new table such as `setmetatable({}, mt)` is the only table that call gives the metatable. A value stored under `__newindex` that the scanner cannot place counts as any table, and a function counts as none. A write through anything else, such as a field path, a call result, a parameter or a global, may reach any table except one whose local is only ever indexed: never read as a value, passed, returned, stored, aliased or used as a method receiver.

Tables keep their identity across aliases, fields, `self` and parameters, and through calls that hand a table back: `select`, `table.unpack`, `assert`, the results of `rawset`, `setmetatable`, `pcall`, `xpcall`, `coroutine.resume` and `coroutine.wrap`, and a function called before its body is read, such as an immediately invoked function or a `pcall` callback. Field writes through any path, `rawset`, `table.insert`, `table.remove`, `table.clear`, `table.clone`, `table.pack`, `table.create` and `table.move` are followed. A small local function that receives a table is replayed for what it does to it, such as `self.id = id`. A metatable is read when it is used, so a change after `setmetatable`, including one through `getmetatable`, counts. A value the script stores in `_G`, `shared` or the script environment through `getfenv()`, under a name or an integer key, is read back in the same script. After a write through `getfenv()` under a key the scanner cannot read, a global or environment key the script did not store has the written value as a candidate.

An ID shaped argument passed to a global called by a computed name, such as `_G[name](id)`, gets the same finding, together with BG004.

A function in the same script that passes its argument to `require` is checked where it is called. The finding is reported at the call site, with evidence such as `FAKE_load(999000000000001) [via require(id)]`. Methods, `__call`, `__index`, `__newindex` and operator metamethods such as `__add` and `__concat`, coroutines, class style constructors, `gsub` callbacks, `gmatch` loops, and `for k, v in next, t` are followed up to a depth of 3. Past the replay limits, an ID shaped argument still gets a medium confidence finding, also inside a table argument up to three levels deep, when the function holds or calls a `require` whose target may be something other than a local module. A function whose every `require` loads a local module, such as `require(script.Parent.Util)` in an event callback, cannot pass the argument to it and gets no such finding. A wrapper in another module is not followed, and neither is a value another script stores in `_G` or `shared`.

String targets such as `./Signal` and `@pkg/x` are local and do not produce a finding. A string that contains only digits is treated as a numeric ID. Instance shaped targets rooted at `game`, `workspace`, `script`, or a service lookup are also treated as local.

```luau
local loadModule = require
local FAKE_ID = 999000000000001
loadModule(FAKE_ID)
```

## Why it matters

A numeric module load can run source that is not present in the scanned file. Its contents can change outside the current review.

## False positives

Some admin systems and older libraries load a reviewed module by asset ID. Confirm who controls the module and whether remote updates are acceptable. A trusted ID entry is a narrow exception. Do not copy IDs from other projects.

An unknown function parameter or opaque call result can produce a low confidence finding when the scanner cannot prove that it refers to local code. Review the value's origin before suppressing it.

Using `require` as a value is reported at high severity and medium confidence by design. This includes storing it in a table such as `{ require = require }`, assigning it to `_G` or `shared`, passing it to another function, or returning it. Legitimate code almost never does this, and a stored `require` can later load a module by ID out of the scanner's sight. Calls through `pcall`, `xpcall`, `task.spawn`, `task.defer`, `task.delay`, `coroutine.wrap`, `coroutine.create`, `spawn`, and `delay` are treated as calls instead. If a reviewed dependency injection table needs this shape, suppress the finding at that path with a reason.

## Suppression

Prefer `trusted_asset_ids` when one reviewed module ID is expected. A trusted ID removes a finding only when the target is fully resolved, every possible ID is trusted, and the `require` argument is a constant: built from literals and from locals that are declared once from such values, never assigned again, and read in the function that declares them. Another variable with the same name, such as a parameter of another function, does not change this. `require(999000000000001)`, `local ID = 999000000000001; require(ID)` and `require(c and ID or ID2)` with both IDs trusted are constants.

A trusted ID read any other way is still reported, at medium confidence with the evidence `trusted asset id, not a constant target`: from a table such as a configuration table, from a value object or an attribute (BG002), from a global, a call result, a function parameter, or a variable of an enclosing function. A trusted ID among unknown values, such as an ID changed in a loop or a table passed to an unknown function, is reported as a candidate. Suppress such a reviewed loader by path. For a local exception, add a suppression for `BG001` with a path glob or fingerprint and a required reason. Add an expiry when the exception is temporary.

```toml
[[suppressions]]
rule = "BG001"
path = "/FAKE_Admin/Loader"
reason = "FAKE reviewed admin module for this test project"
```
